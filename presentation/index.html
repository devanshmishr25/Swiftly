The Problem

Finding help locally is broken.

🔍
No Central Platform
People rely on word-of-mouth, scattered WhatsApp groups, or outdated directories to find plumbers, electricians, tutors.
⏳
Slow & Unreliable
No real-time booking, no status tracking, and no messaging channel between customer and provider once a job is booked.
🚫
Zero Verification
Anyone can claim to be a professional. Customers have no way to verify a provider's identity or credentials before hiring.

💡 Swiftly solves all three — with a centralized marketplace, real-time communication via Socket.IO, and a mandatory admin approval workflow for every service provider.

Database Design

4 Mongoose models.

👤
User
name, email, phone, password (hashed), role (customer/provider/admin), location, category, isApproved, isVerified, OTP fields · timestamps
📅
Booking
service (ref), customer (ref), provider (ref), status (pending/accepted/completed/cancelled), scheduledDate, totalPrice, notes · timestamps
🛠️
Service
title, category, description, provider (ref), price, location, icon · Linked to booking for categorized search
💬
Message
sender (ref), recipient (ref), booking (ref), text · Persisted per booking for full chat history retrieval

All collections use Mongoose population (`.populate()`) to resolve references — bookings include full customer, provider, and service objects for rich dashboard display.

Security & Best Practices

Built secure from day one.

🔒
No Hardcoded Secrets
JWT secret, admin credentials, and MongoDB URI all live in .env — excluded from repository via .gitignore
🛡️
Role-Based Middleware
Every protected route goes through JWT verification + role check middleware before any controller logic runs
🔑
Bcrypt Hashing
All passwords hashed with bcryptjs (10 salt rounds) — plain text is never stored in the database
🚪
Route Guards
Providers are redirected away from customer pages, admin panel requires admin role — enforced both on frontend and backend
🔄
Auto-Logout on 401
When a token expires, the app automatically clears storage and redirects the user to /login — no stale session risk
⏱️
OTP Expiry
Password-reset OTPs have a stored expiry timestamp — expired OTPs are rejected before any password change is allowed
